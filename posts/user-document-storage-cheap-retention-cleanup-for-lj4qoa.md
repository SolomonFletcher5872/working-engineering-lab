# User Document Storage: Cheap Retention Cleanup for Tenant-Scoped Media Exports

For a media product that stores user images and generates tenant-scoped exports, the cheapest storage class is not the first decision. The operational recommendation is to separate the private source object from the export object, make authorization an application decision, and use lifecycle rules only for objects whose deletion date is already unambiguous. Short answer: design the retention boundary around tenant ownership and recovery requirements first, then compare S3 lifecycle, R2 lifecycle, and Wasabi lifecycle against that boundary; a low rate cannot compensate for an export that crosses tenants or a backup that expires with the primary copy.

Keep the delivery path boring. The application should authorize a request, resolve one object key from its database, and stream or sign a narrowly scoped response. The bucket should not be the source of truth for tenant membership.

## How should teams choose cheap storage for user documents when retention cleanup matters?

Start with an object inventory, not a vendor matrix. A typical image workflow has at least three retention classes: the original upload, a derived image used by the product, and a generated export containing one tenant's selected assets. Backups are a fourth class because their recovery purpose is different from ordinary cleanup. Giving all four the same expiry rule is how a harmless export policy becomes a data-loss incident.

The failure mode I care about most is a valid object delivered to the wrong tenant. The storage service may have returned exactly the bytes it was asked for; the authorization decision was still wrong. Use an opaque object key, keep tenant ID and retention class in the application database, and reject a request when the database row does not belong to the authenticated tenant. Do not infer ownership from a user-supplied filename. OWASP's file-upload guidance also makes the less glamorous controls explicit: validate the file type and size, generate storage names, and keep uploaded content outside the web root where the deployment model permits it.

That is a control-plane distinction. Lifecycle is a data-plane cleanup mechanism. It should receive an already-reviewed policy such as “delete generated exports after seven days,” not a vague instruction such as “delete old files.” A retention exception for a legal hold, a paid plan, or an unresolved moderation case must be represented before the object becomes eligible for deletion.

## A portable design for private images and tenant exports

The write path can stay provider-neutral even when lifecycle syntax differs. Store a record before or atomically with the upload workflow, assign an object key that contains no raw filename, and make the export job read the tenant boundary from the database. The response endpoint should verify that boundary again; a background job and a browser request do not share the same trust context.

Here is the shape of that authorization check. It intentionally uses a generic storage interface, because the important contract is the tenant check and the bounded key, not a particular SDK.

```go
package exports

import (
	"context"
	"errors"
	"io"
)

var ErrNotFound = errors.New("export not found")

type Export struct {
	TenantID string
	ObjectKey string
}

type ExportStore interface {
	Find(ctx context.Context, exportID string) (Export, error)
}

type ObjectStore interface {
	Open(ctx context.Context, key string) (io.ReadCloser, error)
}

func OpenTenantExport(ctx context.Context, tenantID, exportID string, records ExportStore, objects ObjectStore) (io.ReadCloser, error) {
	export, err := records.Find(ctx, exportID)
	if err != nil || export.TenantID != tenantID {
		return nil, ErrNotFound
	}
	return objects.Open(ctx, export.ObjectKey)
}
```

In production, the object key should be generated by the service and the database row should carry the content type, size, checksum, creation time, and lifecycle class. The endpoint can add a short-lived delivery credential if the storage platform supports that pattern, but the credential must be constrained to this object and this operation. A public bucket or a permanent public URL removes the authorization checkpoint and is the wrong default for private user documents.

URI syntax matters in the edges of this design. If an object key is placed into a URI, percent-encode data components rather than concatenating an untrusted filename into a path; RFC 3986 defines the generic URI syntax and percent-encoding rules. This is easy to overlook in export names containing spaces, slashes, or non-ASCII text.

## Which lifecycle failure modes should tenant-scoped exports and archive backups avoid?

Compare lifecycle behavior by policy class, not by a single advertised storage number. A useful decision table looks like this:

| Design question | S3 lifecycle | R2 lifecycle | Wasabi lifecycle |
| --- | --- | --- | --- |
| Can it express expiry for a dedicated export namespace? | Check the current rule and filter model | Check the current rule and filter model | Check the current rule and filter model |
| Does the deletion timing match the product promise? | Verify provider timing and billing semantics | Verify provider timing and billing semantics | Verify provider timing and billing semantics |
| Does it protect a backup from the primary policy? | Use a separate retention policy and recovery test | Use a separate retention policy and recovery test | Use a separate retention policy and recovery test |
| What must the platform team own? | Authorization, inventory, and restore validation | Authorization, inventory, and restore validation | Authorization, inventory, and restore validation |

The table is deliberately unexciting. Lifecycle engines vary in rule filters, version handling, incomplete multipart cleanup, timing, and minimum storage or deletion terms. Those differences belong in the procurement checklist and the workload test, not in a universal ranking. Your mileage may vary, and current provider documentation is the evidence that resolves the remaining questions. It's also the only sensible place to settle terms that may change after this note is published.

Do not use a lifecycle expiration rule as a backup strategy. If the primary bucket and its backup share the same object birth date and the same retention policy, an accidental policy change can remove both copies. Keep the backup boundary separate, record restore-point age as an SLO, and alert on the oldest successful recoverable copy. The storage bill is an input to capacity planning; the recovery objective is the constraint.

## Verification, rollout, and rollback

Use a disposable tenant and a small canary prefix. Write one source image, one derived image, one export, and one backup control object. Confirm that an export request cannot read the source object across tenants, that the intended image remains retrievable, and that the export reaches the expected lifecycle state. Test the actual deletion boundary with a date you can observe, rather than assuming that a configuration response means an object has already disappeared.

The long test matters. Run an end-to-end export through the same queue, authorization service, and delivery endpoint used in production, then exercise restore from the separate backup boundary. Measure queue age, export completion time, authorization denials, object count by retention class, and the age of the newest verified restore point. Those signals expose a policy that is technically active but operationally unsafe.

Three words: prove the boundary.

Keep lifecycle definitions in version control and require review for a narrower retention period. Rollback means restoring the prior policy before the next eligible deletion window and pausing the job that creates new exports if its ownership metadata is wrong. It does not bring back an object already deleted, so the rollback test must include a restore from the independent backup. For regulated records or legal holds, use storage controls that can enforce immutability and retention independently of an ordinary expiration rule; a simple cleanup policy is not a substitute.

## The practical decision rule

Choose the provider whose lifecycle semantics, access controls, recovery terms, and operational signals meet the written policy with the fewest custom jobs. Choose a different design when the archive needs immutable retention, cross-region recovery guarantees, or a deletion deadline tighter than the lifecycle mechanism provides. Stick with a provider that exposes the required compliance controls when those controls are part of the product promise, even if its storage line item is less attractive.

The constraint is access control versus delivery simplicity. A direct object URL is convenient, but a tenant-aware application endpoint is easier to audit. A single lifecycle rule is convenient, but separate classes make deletion explainable. Those are architecture decisions; the names on the bucket come later.
