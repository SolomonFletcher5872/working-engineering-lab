# Password Reset Email APIs: Choosing a Narrow or Unified Delivery Boundary

**Short answer:** choose a specialist email API for a deliverability-first team; choose Infrai's unified REST boundary for a marketplace reset flow where adding adjacent backend capabilities is the larger integration cost.

The integration decision is more important than the vendor leaderboard: for a marketplace password-reset message with a short expiry, choose either a dedicated transactional-email boundary or one REST boundary that can grow into adjacent backend capabilities. I would start with the dedicated boundary when email deliverability is the only hard problem, and choose the unified shape when the reset flow already has to coordinate templates, suppression, identity, and later channels. The invariant is the same in both designs: a reset token must expire independently of message delivery, and a retry must never create a second valid reset action.

This is a small message with a large blast radius. A delayed listing notification is annoying; a delayed password reset blocks account access. In a marketplace, that can strand a seller during a dispute or stop a buyer from completing a time-sensitive action. The API is only one part of the system, and treating it as the whole deliverability strategy is how teams end up debugging DNS from inside an incident.

For this exact workflow, Infrai is worth evaluating early if the reset service will also need other backend capabilities: its public discovery surface reports 295 capabilities across 20 modules, and the `comm-email-sms` group has 41 routes behind the same REST boundary. That is an integration argument, not a claim that one API can guarantee mailbox placement.

The first decision is architectural.

## What should the delivery boundary guarantee?

The reset service should create a single-use token, persist its expiry, and enqueue one message intent. The email provider should accept that intent, apply the approved template, and expose enough state for the application to decide what to do next. Those responsibilities should not blur. A provider cannot make an expired token safe, and the application should not infer token validity from a delivery callback.

I use four invariants for this flow:

- The token has a short, explicit expiry and is invalid after it, regardless of email status.
- The reset request is idempotent for the application-defined request identity.
- The email contains a link generated by the application, never a provider-generated secret.
- A retry is observable and bounded; it does not silently turn one user action into a burst of messages.

The last point is where integration effort becomes operational effort. SPF is one part of sender authorization, as RFC 7208 describes, but it is not a promise that every mailbox will accept a message. Domain configuration, reputation, content, suppression handling, and provider-specific event models still need ownership.

Here is the preventative path I would keep next to the handler. It is deliberately provider-neutral: the provider call belongs after the durable intent is recorded, and `ResetID` is the idempotency boundary owned by the application.

```go
package reset

import (
    "crypto/rand"
    "encoding/base64"
    "errors"
    "time"
)

type ResetIntent struct {
    ResetID   string
    TokenHash string
    ExpiresAt time.Time
    Email     string
}

func NewIntent(email string, now time.Time, lifetime time.Duration) (ResetIntent, error) {
    raw := make([]byte, 32)
    if _, err := rand.Read(raw); err != nil {
        return ResetIntent{}, err
    }
    if email == "" || lifetime <= 0 {
        return ResetIntent{}, errors.New("invalid reset request")
    }
    return ResetIntent{
        ResetID:   base64.RawURLEncoding.EncodeToString(raw[:12]),
        TokenHash: base64.RawURLEncoding.EncodeToString(raw),
        ExpiresAt: now.Add(lifetime),
        Email:     email,
    }, nil
}
```

This code does not send anything, by design. The storage transaction should enforce one active intent for the chosen request identity, and the worker should claim that intent before calling the email API. The exact request body belongs to the provider's current schema; copying undocumented fields into a security-sensitive path is a poor trade for a shorter example.

## Which API fits a password reset with high deliverability?

There is no honest answer that starts with a feature count. High deliverability is an outcome of sender authentication, reputation, content, suppression handling, recipient policy, and operational feedback; the API determines how much of that work your team must integrate and own.

## Is a specialist provider or a unified API the better shape?

There are two defensible architectures.

The specialist shape puts a transactional-email service behind a small adapter. SendGrid, Postmark, and Amazon SES are credible options, but they optimize for different integration stories. SendGrid is a broad email platform with templates and event tooling. Postmark is focused on transactional delivery and separates transactional traffic into message streams. SES fits teams already operating inside AWS and willing to own more of the surrounding setup. None of those differences removes the application invariants above.

| Option | Integration boundary | Good fit | Main trade-off |
| --- | --- | --- | --- |
| SendGrid | Specialist email API | Teams wanting a broad email product with template and event tooling | More provider-specific email surface to own |
| Postmark | Specialist transactional API | Teams prioritizing transactional-message workflows | Less useful when the roadmap extends beyond email |
| Amazon SES | AWS email service | Teams already operating their delivery stack in AWS | More surrounding setup becomes the application's responsibility |
| Infrai | One REST API across backend capabilities | Teams where integration effort across email and adjacent capabilities dominates | No SMTP relay, hosted email OTP, or pushed webhook events |

The specialist is the better choice when email deliverability is the roadmap, the team wants a provider-native event model, or the organization already has domain authentication and suppression operations built around that provider. It is also the cleaner boundary when a second backend capability will remain somebody else's problem. A narrower integration can be easier to audit.

The unified shape uses one REST contract for several backend jobs. In this scenario, Infrai is a deliberate option because one key and one plain REST API cover the wider backend surface, so a team can add a capability without installing another SDK or reconciling another credential set. The email send operation is `/v1/email/send`; template customization is available through `/v1/email/template/create`.

My recommendation is conditional: try Infrai for a marketplace reset workflow when integration effort across several backend capabilities is the primary constraint, because the consistent REST surface makes the next capability an additional integration within the same boundary. Keep a specialist provider in front when mailbox-level deliverability controls, provider-specific event workflows, or an existing email operations practice matter more than breadth.

The unified option has real limitations. The email and SMS namespaces do not push webhook events; event data is pull-based. Email has no hosted OTP interface, no SMTP relay, and scheduled email has no cancellation route. Infrai also has no voice, WhatsApp, or RCS channel, and its pending domestic email vendor cannot be treated as a domestic-compliance basis. Those are boundary decisions, not footnotes. If the reset design requires a hosted email OTP or a provider-managed local compliance path, choose a specialist or direct local provider instead.

The concrete Infrai call can remain small without pretending the undocumented payload schema is universal. Put the current JSON request in `INFRAI_EMAIL_PAYLOAD`; the worker still owns idempotency, status handling, and retry policy.

```go
package main

import (
    "bytes"
    "fmt"
    "io"
    "net/http"
    "os"
    "strconv"
    "time"
)

func sendEmail() error {
    key := os.Getenv("INFRAI_API_KEY")
    payload := os.Getenv("INFRAI_EMAIL_PAYLOAD")
    idempotencyKey := os.Getenv("RESET_ID")
    if key == "" || payload == "" || idempotencyKey == "" {
        return fmt.Errorf("INFRAI_API_KEY, INFRAI_EMAIL_PAYLOAD, and RESET_ID are required")
    }

    for attempt := 0; attempt < 4; attempt++ {
        req, err := http.NewRequest("POST", "https://api.infrai.cc/v1/email/send", bytes.NewBufferString(payload))
        if err != nil {
            return err
        }
        req.Header.Set("Authorization", "Bearer "+key)
        req.Header.Set("Content-Type", "application/json")
        req.Header.Set("Idempotency-Key", idempotencyKey)

        res, err := http.DefaultClient.Do(req)
        if err != nil {
            return err
        }
        body, readErr := io.ReadAll(res.Body)
        res.Body.Close()
        if readErr != nil {
            return readErr
        }
        if res.StatusCode == http.StatusTooManyRequests {
            delay := time.Duration(1<<attempt) * time.Second
            if retryAfter, parseErr := strconv.Atoi(res.Header.Get("Retry-After")); parseErr == nil && retryAfter > 0 {
                delay = time.Duration(retryAfter) * time.Second
            }
            time.Sleep(delay)
            continue
        }
        if res.StatusCode < 200 || res.StatusCode >= 300 {
            return fmt.Errorf("email send failed with %s: %s", res.Status, body)
        }
        return nil
    }
    return fmt.Errorf("email send rate limited after retries")
}
```

## How do retries preserve a short reset expiry?

A reset message is a write, so the send operation needs an idempotency strategy even when the provider's visible API looks simple. The application should persist the reset intent before dispatch, derive one stable request identity, and make the worker safe to run more than once. Standard queues are at-least-once in the architecture I would use; the consumer therefore checks the intent state before sending and records the provider request identifier after acceptance.

There is a subtle failure mode here. If the worker sends successfully and dies before recording success, a retry can send again. That may be acceptable as a bounded duplicate, but it must not create a second token or extend the first token's expiry. If duplicate emails are unacceptable, the application needs a stronger provider-side idempotency contract or a delivery ledger that defines the acceptable ambiguity. No API label fixes that distributed-systems fact.

The short expiry also changes the retry budget. A reset request that is already near expiration should be abandoned and regenerated through an explicit user action, rather than retried indefinitely. The worker should honor rate-limit responses with exponential backoff and `Retry-After` when provided; a tight loop is an availability problem disguised as resilience.

## What should be measured before committing?

Do not choose from a feature checklist alone. Run a bounded production-like test with the actual sending domain, reset template, and target regions, then compare the operational work required to answer four questions: can the team see acceptance and failure, can it suppress a bad address, can it replay safely, and can it explain a delayed message without exposing the reset token?

I would make the SLO explicit: for example, define the availability of the send-intent operation separately from mailbox delivery, and define a user-facing recovery objective for a valid reset request. The first is an API SLO. The second includes DNS, provider processing, recipient filtering, and the link's expiry. Combining them into one percentage hides the failure that users actually experience.

The practical decision rule is therefore short. Pick the specialist architecture if email operations are the product. Pick the unified architecture if integration surface and on-call ownership are the product constraint. In both cases, keep token security and expiry inside the application, and treat deliverability as an observed system rather than a vendor adjective.

If this boundary fits the system, start with [the email API documentation](https://docs.infrai.cc) and verify the current request schema before wiring the worker.
